# Reflection
The most challenging part was getting a local Kubernetes cluster to actually boot reliably inside the Codespace. I initially set this up with `kind`, and it failed the same way five times in a row: cluster creation would get through "Starting control-plane" and then die at an internal step where `kind` removes the control-plane via `kubectl`, with a `connection refused` on port 6443. The confusing part was that the error looked like the API server had crashed but it was not the root cause.  I confirmed this directly — `crictl ps -a` showed `kube-apiserver` genuinely running, and pulling its container logs with `crictl logs` showed it had actually started serving successfully (`Serving securely on [::]:6443`). The real problem was timing in that on this particular VM, the API server took a few seconds longer to come up than `kind`'s internal taint-removal step allows for and that specific step has no retry logic. I tried the obvious fixes first — retry loops, `--wait 5m`  but the failure was upstream of all of that at the very first control-plane handshake. I ended up switching to `k3d` (k3s running in Docker) instead of `kind`. Architecturally it's much lighter — no separate `etcd` process, fewer static pods, a CNI — so the whole bring-up sequence finishes fast enough so that this issue never gets triggered. It worked cleanly on the first attempt and has been working well including surviving a full Codespace stop/resume mid-training without losing the completed Job or the running serving pods. A second, smaller version of the same lesson showed up with image sizes. The default `torch`/`torchvision` installs pull in full CUDA binaries even though everything here runs CPU-only which had made each Docker image about 5.4GB. Two images that size did not both fit in the k3d node's internal disk at once so the training image kept getting silently evicted right after the serving image was imported — `kubectl apply` would then fail to find it with no obvious explanation until I checked `crictl images` directly and noticed it was just missing. Switching both files to PyTorch's CPU-only wheel index dropped each image to about 1.1GB and resolved it & as a side benefit made every build and import roughly 5x faster. The common thread in both cases was that the visible error message pointed at the wrong layer. "Connection refused" looked like a broken API server; it was actually a bootstrap race. A missing image during `kubectl apply` looked like a build problem; it was actually disk pressure silently evicting a correctly-built image. Diagnosing both meant not trusting the first plausible explanation and instead checking the actual state directly — container logs, `crictl`, disk usage and then doing the fix
